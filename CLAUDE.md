# takenbyninjas.com — Blog + TomBot

Static blog published from Google Docs, with a RAG-based AI chatbot (TomBot). Hosted on Netlify with auto-deploy on push to main.

## Tech stack

- **Blog**: Python publish pipeline → static HTML/CSS. Vanilla JS. CRT/teletext theme.
- **TomBot**: Netlify Function (Node.js), Claude Sonnet, Voyage AI embeddings, Nile pgvector DB.
- **Hosting**: Netlify (every push = 1 build = costs money).

## Commands

```bash
# Preview locally
npx http-server -p 8000              # or: python3 -m http.server 8000

# Publish a post (interactive — opens preview, waits for approval)
python3 publish.py "Post Title"

# Regenerate homepage / archive
python3 generate_homepage.py
python3 generate_archive.py

# TomBot: update content pipeline
python3 scripts/parse_content.py      # markdown → JSON
python3 scripts/load_content_v3.py    # JSON → embeddings → DB

# TomBot: run locally
unset ANTHROPIC_API_KEY && netlify dev --port 8888
```

## Generated files — do NOT edit

These are generated by scripts. Edit the generator, not the output:
- `index.html` ← `generate_homepage.py`
- `words/index.html` ← `generate_archive.py`
- `words/{slug}/index.html` ← `publish.py`
- `sitemap.xml` ← `generate_sitemap.py` (also run by publish.py)

Hand-maintained (edit directly, do NOT regenerate):
- `about/index.html` — bespoke HTML (portrait, timeline). The Google Doc is copy source only; running `publish.py "about"` FLATTENS the page. Port Doc copy changes by hand.
- `projects/index.html`, `projects/tombot/index.html`

Before committing regenerated files, verify generators match output:
```bash
python3 generate_archive.py && git diff words/index.html
python3 generate_homepage.py && git diff index.html
```
If diff shows unexpected changes, the generator is out of sync — fix the generator, not the HTML.

## Publishing workflow

Use the `publish-post` skill (`.claude/skills/publish-post/SKILL.md`) — it holds the full workflow, prompt-answer patterns, and the QA checklist. Short version:

- Draft/iterate locally: `python3 scripts/publish_local.py "doc-name"` (answers publish.py's prompts by reading them, never pushes). Never pipe blind answers into `publish.py` — its prompt count varies.
- Push only on Tom's explicit go, as a batch.

## Google Docs markup

Frontmatter fields (at top of Google Doc): `url`, `date`, `browser-title` (SEO title tag), `meta-desc`, `tags`, `no-crt`, `hero-image`.

Inline markers:
- `[HOZ]` → `<hr />`
- `[CAPTION]` → `<figcaption>`
- `[ENDSNIP]` → excerpt end marker (content above it = homepage excerpt)
- `[QUOTE]` → `<blockquote>`

The pipeline interprets Doc *intent*, not raw formatting:
- URL slugs are always lowercased (site convention: all URLs lowercase).
- Heading styling on a soft-return line (Docs degrades it to bold + heading-blue text) is promoted back to a real `<h3>`.
- Whitespace noise is normalised: tag-only/empty paragraphs skipped, edge soft-returns trimmed, blank-line runs capped.

## Site conventions

- All URLs lowercase, always.
- Homepage featured-post images always link to the post (generate_homepage.py wraps them).
- Every page has a canonical tag (`html_head(canonical_path=...)`; `SITE_URL` in config).
- Umami tag must carry `data-domains="takenbyninjas.com"` so localhost never tracks.
- Blog post images: 1024px wide standard; hero images ~2:1 landscape (supply larger, pipeline downscales).
- `mockups/` is untracked scratch — never commit it (`git add -A -- . ':!mockups'`).

Soft returns (`\u000b`) in Google Docs become `\n` in processing — this matters for line-break handling in publish.py.

## Known quirks

- `publish.py` runs twice when piped input (`<<< "yes"`) — EOF on second prompt is expected.
- `publish.py` sometimes asks an extra "HTML has structural errors. Continue anyway?" — its validator false-positives on unclosed tags mid-flow; the final output is balanced. `scripts/publish_local.py` answers it yes automatically.
- Google OAuth token (`token.json`) can expire with `invalid_grant` — delete it and have Tom run `publish.py` in his own terminal to re-auth (opens browser consent).
- Netlify serves URLs case-insensitively via 301 to lowercase.
- `sips` crop flag: use `--cropToHeightWidth`, not `-c`.
- Image format detection uses magic bytes (PNGs were being saved as .jpg).
- CRT CSS selectors need both `p > img` and `p > a > img` for linked images.
- Caption paragraphs can contain inline images — `caption_handled` flag prevents skipping.

## TomBot — architecture details

TomBot is a RAG chatbot at `/projects/tombot/` that answers questions about Tom's career. It's intentionally a retrieval bot, not a creative assistant — it only answers questions it has training data for.

### Content pipeline (source of truth → DB)
```
docs/tombot/tombot-content-v3.md          # Source of truth — edit THIS file
  → python3 scripts/parse_content.py      # markdown → JSON
  → scripts/parsed_content.json           # intermediate (don't edit)
  → python3 scripts/load_content_v3.py    # JSON → Voyage embeddings → pgvector DB
```

### RAG flow (user query → answer)
1. User query → Voyage AI embedding
2. Match against pre-embedded question variations (threshold: 0.70)
3. If no match → bot deflects gracefully (never hallucinate)
4. TOP_K=1 (single match to prevent cross-section bleed)
5. Retrieved content → Claude Sonnet → streamed response

### Key design decisions
- **System prompt is behavioural only** — no facts about Tom. All factual content comes from RAG.
- **Follow-up suggestions** — only suggest topics from `<follow_up_suggestions>` block in retrieved content. Never invent topics.
- **DB wipe on reload** — `load_content_v3.py` deletes ALL chunks before inserting (no stale data).
- **Dates in retrieved content are always correct.** If they conflict with Claude's training data, retrieved content wins.

### Content format (tombot-content-v3.md)
```markdown
## SECTION.ID

**Questions that route here:**
- Question variation 1
- Question variation 2

**Suggested follow-ups:**
- "follow-up question" [TARGET.SECTION]

Answer content here.
```
